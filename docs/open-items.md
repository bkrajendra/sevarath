# Open Items / Workaround Log

> Back to [README](../README.md) · See also [Specification](./specification.md) · [Architecture & Design](./architecture.md) · [Implementation Plan](./plan.md)

Running log of gaps, workaround decisions, and things that need a human look, made while implementing the plan. Each entry: what was decided/skipped, why, and what would change the decision. Review and close/convert-to-ticket items as the team sees them.

| # | Area | Item | Decision taken | Needs review? |
|---|---|---|---|---|
| 1 | Dev environment | This sandbox has no PostGIS extension available (not installed, no network to `apt-get install postgresql-16-postgis-3`) and no running Docker daemon, so `docker-compose.yml`'s `postgis/postgis` image can't be used here. | Started the sandbox's own `postgresql` and `redis-server` packages directly (`service postgresql start`, `redis-server --daemonize yes --port 6380`), created a local `sevarath` role/db, and ran migrations `0000`/`0001` **with the `campus_locations`/`campus_roads`/`campus_restricted_zones` `CREATE TABLE` statements stripped** (applied via `psql -f`, not through `drizzle-kit migrate`, so the real migration files/tracking are untouched). This gives a working Postgres for `users`/`drivers`/`vehicles`/`rides`/`ride_events` and everything added for Phase 4, but campus/map features cannot be exercised against this local DB. Real deployments still use the unmodified migrations against a real PostGIS-enabled Postgres - no production file was changed. | No - sandbox-only, doesn't affect the repo. |
| 2 | Schema / Dispatch | `architecture.md §4.2` calls for a "PostGIS distance query" for nearest-driver matching, but (a) there is no `drivers` location column or `driver_locations` table at all yet - live driver position is explicitly Redis-only per `specification.md §6` and belongs to Phase 5 - and (b) PostGIS isn't actually available in this dev sandbox (see #1). | Added a plain `current_latitude`/`current_longitude`/`location_updated_at` snapshot to the `drivers` table (not PostGIS geometry - consistent with how `rides.pickup_latitude/longitude` already work) plus a `POST /api/v1/drivers/location` endpoint (already listed as representative API surface in `architecture.md §6`) so a driver can push a coarse location even before Phase 5's live pipeline exists. Nearest-driver matching in `dispatch` uses a Haversine formula in plain SQL against these columns, not `ST_Distance`. | **Yes** - when Phase 5 lands the real Redis-backed live location pipeline, decide whether dispatch should read from Redis instead (fresher) and whether this DB snapshot stays as a cold-start/fallback source or gets removed. |
| 3 | Events / Outbox | `EventsModule`'s `OutboxPublisherService` (Phase 4, `architecture.md §4.3`) pushes jobs onto a new `domain-events` BullMQ queue (`registerQueue`), but no consumer/processor reads that queue yet - `rides`/`dispatch`/`notifications`/the WebSocket gateway are all later phases/tasks. | Shipped the publisher anyway, since the goal of this task was the outbox infra other modules will plug into, not the consumers. Jobs will accumulate unread in Redis (`domain-events` queue) in any environment this boots in, for as long as no worker/processor is registered against that queue name. There's no backpressure or TTL on the queue today. | **Yes** - before this is deployed anywhere persistent (including this sandbox, if it stays up), either add a processor consuming `domain-events`, or stop running `OutboxPublisherService`/`BullModule.forRoot` until one exists, so Redis memory doesn't grow unbounded. |
| 4 | Events / Outbox | The publisher's poll query (`OutboxPublisherService.pollAndPublish`) is a plain `SELECT ... ORDER BY created_at ASC LIMIT 20` over `outbox_events WHERE published_at IS NULL`, not a locking `SELECT ... FOR UPDATE SKIP LOCKED`. With more than one publisher instance running concurrently, two instances could pick up and enqueue the same row before either marks it `published_at`, double-publishing it downstream. | Left non-locking for now: today's deployment runs exactly one `OutboxPublisherService` instance (it's a singleton `@Interval` poller inside the single API process, not horizontally scaled), so the race can't occur in practice, and this keeps the query simple/portable across the Drizzle version pinned here rather than hand-writing raw `FOR UPDATE SKIP LOCKED` SQL. | **Yes** - if the API process is ever scaled to multiple replicas (or the publisher is split into its own worker process with >1 replica), add row locking (`FOR UPDATE SKIP LOCKED` via Drizzle's raw SQL escape hatch) or move to a single dedicated publisher replica, before that happens. |
| 5 | Dependencies / Build | The latest major versions of `@nestjs/schedule` (12.x) and `@nestjs/bullmq` (12.x, pulling in `bullmq` 6.x) have gone ESM-only (`"type": "module"`, no CJS build). This repo's `apps/api` is CommonJS end-to-end (`tsconfig.json` `module: commonjs`, `ts-jest`), so those versions fail to load under Jest (`SyntaxError: Unexpected token 'export'`) and would need a Jest/ESM migration to use. | Pinned exact, older, CJS-built versions instead: `@nestjs/schedule@4.1.2`, `@nestjs/bullmq@10.2.3`, `bullmq@5.81.5` (all still within `@nestjs/core`'s `^10.x` peer-dependency range this repo already uses). Also had to set `msgpackr-extract: true` under `allowBuilds` in `pnpm-workspace.yaml` (it was a placeholder `set this to true or false` entry) so `bullmq`'s optional native dependency can run its install script; nothing else in `pnpm-workspace.yaml` was changed. | **Yes** - when the repo is ready to move off Nest v10 / adopt ESM, re-evaluate upgrading `@nestjs/schedule`/`@nestjs/bullmq`/`bullmq` to their current majors together with that migration, rather than leaving them pinned behind. |
| 6 | Dependencies / Build | `@nestjs/event-emitter`'s latest majors (12.x) target newer Nest versions; needed to confirm a version compatible with this repo's pinned Nest v10 / CommonJS setup (same ESM-only risk as #5). | Checked before trusting `pnpm add`'s default resolution and pinned `@nestjs/event-emitter@2.1.1` explicitly (peer range `^8‖^9‖^10` for `@nestjs/core`/`@nestjs/common`, CJS `main` entry, no `"type": "module"`). Its only dependency, `eventemitter2@6.4.9`, is also CJS. | No - verified compatible, no ESM issue hit. |
| 7 | Rides / State machine | `specification.md §5`'s diagram plus `§8`'s edge-case table don't fully agree on two points, so `RIDE_TRANSITIONS` in `rides/ride-state-machine.ts` had to make a judgment call reconciling them: (a) whether `RIDE_STARTED`/`DRIVER_EN_ROUTE_TO_DESTINATION` are cancellable, (b) what "driver cancels" transitions to. | (a) Took §5's "cancellable while permitted by ride state" together with its diagram ordering to mean cancellation stops being offered once the ride has physically started, i.e. `RIDE_STARTED` and `DRIVER_EN_ROUTE_TO_DESTINATION` have **no** `CANCELLED_*` outgoing edge (only `DRIVER_ASSIGNED` through `DRIVER_ARRIVED` do). (b) §8's edge-case table literally says "Driver cancels → Ride returns to dispatch / `SEARCHING_DRIVER`" (re-offer to a new driver without the rider re-requesting), but the `ride_status` enum has no "returned to dispatch" state distinct from a fresh `SEARCHING_DRIVER` ride, and implementing real re-dispatch needs the (not-yet-built) Dispatch module to re-run matching while excluding the cancelling driver. Implemented the simpler, terminal `CANCELLED_BY_DRIVER` transition for now (`rides.service.ts#cancel`) - `cancel()` picks `CANCELLED_BY_USER` or `CANCELLED_BY_DRIVER` by the requester's role but both are terminal today. The full `RIDE_TRANSITIONS` table is in `apps/api/src/rides/ride-state-machine.ts`. | **Yes** - once the Dispatch module exists, decide whether driver-cancellation should re-open a `SEARCHING_DRIVER` cascade (possibly reusing the same ride row, possibly a new one) rather than terminating the ride outright; this is a real product-behavior decision, not just an implementation detail. |
| 8 | Rides / Completion | `rides.service.ts#complete` accepts `fromStatuses: ['RIDE_STARTED', 'DRIVER_EN_ROUTE_TO_DESTINATION']`, and `#markArrived` accepts `fromStatuses: ['DRIVER_ASSIGNED', 'DRIVER_EN_ROUTE_TO_PICKUP']`, both wider than the single-predecessor edges `RIDE_TRANSITIONS` declares for those statuses. | Nothing in this phase ever populates `DRIVER_EN_ROUTE_TO_DESTINATION` (no location/geofencing pipeline exists until Phase 5/6) or `DRIVER_EN_ROUTE_TO_PICKUP` (this phase's driver endpoints are only `arrived`/`start`/`complete` - no "depart to pickup" action). Without this widening, every ride would get stuck at `DRIVER_ASSIGNED` (unable to ever reach `DRIVER_ARRIVED`) or at `RIDE_STARTED` (unable to ever reach `COMPLETED` once `DRIVER_EN_ROUTE_TO_DESTINATION` is finally wired up and a ride happens to be mid-transition). | **Yes** - once Phase 5/6 location tracking lands and actually drives rides through `DRIVER_EN_ROUTE_TO_PICKUP`/`DRIVER_EN_ROUTE_TO_DESTINATION`, revisit whether these driver actions should narrow back to their single literal predecessor, or deliberately stay permissive as a "skip the intermediate state" allowance. |
| 9 | Rides / Dispatch handoff | `rides.service.ts#create` emits an in-process `EventEmitter2` event `'ride.requested'` (payload: `{ rideId, userId, pickup, destination }`) after its transaction commits, intended to let a future Dispatch module start nearest-driver matching without `RidesModule` importing a not-yet-existing `DispatchModule` (which would become circular once Dispatch needs to read ride state back via `RidesService`). | Added the emitter call and `EventEmitterModule.forRoot()` to `app.module.ts`, but **nothing listens for `'ride.requested'` yet** - no `@OnEvent('ride.requested')` handler exists anywhere in the codebase. The ride row itself is still correct/durable (it really does reach `SEARCHING_DRIVER` in Postgres), but with no listener, no dispatch matching is ever triggered, so every ride will sit in `SEARCHING_DRIVER` forever until a Dispatch module adds that listener. This is deliberately a different mechanism from the durable `outbox_events`/BullMQ pipeline (same-process, fire-and-forget, for decoupling business logic) - see the comment at the `eventEmitter.emit` call site in `rides.service.ts`. | **Yes - blocking.** The Dispatch module task must add an `@OnEvent('ride.requested')` listener (or equivalent) before Phase 4's "nearest driver is offered the ride" deliverable can actually work end-to-end. |
