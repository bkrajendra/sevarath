| 4 | Events / Outbox | The publisher's poll query (`OutboxPublisherService.pollAndPublish`) is a plain `SELECT ... | 7 | Rides / State machine | `specification.md §5`'s diagram plus `§8`'s edge-case table don't fully agree on two points, so `RIDE_TRANSITIONS` in `rides/ride-state-machine.ts` had to make a judgment call reconciling them: (a) whether `RIDE_STARTED`/`DRIVER_EN_ROUTE_TO_DESTINATION` are cancellable, (b) what "driver cancels" transitions to. | (a) Took §5's "cancellable while permitted by ride state" together with its diagram ordering to mean cancellation stops being offered once the ride has physically started, i.e. `RIDE_STARTED` and `DRIVER_EN_ROUTE_TO_DESTINATION` have **no** `CANCELLED_*` outgoing edge (only `DRIVER_ASSIGNED` through `DRIVER_ARRIVED` do). (b) §8's edge-case table literally says "Driver cancels → Ride returns to dispatch / `SEARCHING_DRIVER`" (re-offer to a new driver without the rider re-requesting), but the `ride_status` enum has no "returned to dispatch" state distinct from a fresh `SEARCHING_DRIVER` ride, and implementing real re-dispatch needs the (not-yet-built) Dispatch module to re-run matching while excluding the cancelling driver. Implemented the simpler, terminal `CANCELLED_BY_DRIVER` transition for now (`rides.service.ts#cancel`) - `cancel()` picks `CANCELLED_BY_USER` or `CANCELLED_BY_DRIVER` by the requester's role but both are terminal today. The full `RIDE_TRANSITIONS` table is in `apps/api/src/rides/ride-state-machine.ts`. | **Yes** - once the Dispatch module exists, decide whether driver-cancellation should re-open a `SEARCHING_DRIVER` cascade (possibly reusing the same ride row, possibly a new one) rather than terminating the ride outright; this is a real product-behavior decision, not just an implementation detail. |
| 8 | Rides / Completion | `rides.service.ts#complete` accepts `fromStatuses: ['RIDE_STARTED', 'DRIVER_EN_ROUTE_TO_DESTINATION']`, and `#markArrived` accepts `fromStatuses: ['DRIVER_ASSIGNED', 'DRIVER_EN_ROUTE_TO_PICKUP']`, both wider than the single-predecessor edges `RIDE_TRANSITIONS` declares for those statuses. | Nothing in this phase ever populates `DRIVER_EN_ROUTE_TO_DESTINATION` (no location/geofencing pipeline exists until Phase 5/6) or `DRIVER_EN_ROUTE_TO_PICKUP` (this phase's driver endpoints are only `arrived`/`start`/`complete` - no "depart to pickup" action). Without this widening, every ride would get stuck at `DRIVER_ASSIGNED` (unable to ever reach `DRIVER_ARRIVED`) or at `RIDE_STARTED` (unable to ever reach `COMPLETED` once `DRIVER_EN_ROUTE_TO_DESTINATION` is finally wired up and a ride happens to be mid-transition). | **Yes** - once Phase 5/6 location tracking lands and actually drives rides through `DRIVER_EN_ROUTE_TO_PICKUP`/`DRIVER_EN_ROUTE_TO_DESTINATION`, revisit whether these driver actions should narrow back to their single literal predecessor, or deliberately stay permissive as a "skip the intermediate state" allowance. |
| 9 | Rides / Dispatch handoff | `rides.service.ts#create` emits an in-process `EventEmitter2` event `'ride.requested'` (payload: `{ rideId, userId, pickup, destination }`) after its transaction commits, intended to let a future Dispatch module start nearest-driver matching without `RidesModule` importing a not-yet-existing `DispatchModule` (which would become circular once Dispatch needs to read ride state back via `RidesService`). | Added the emitter call and `EventEmitterModule.forRoot()` to `app.module.ts`, but **nothing listens for `'ride.requested'` yet** - no `@OnEvent('ride.requested')` handler exists anywhere in the codebase. This is deliberately a different mechanism from the durable `outbox_events`/BullMQ pipeline (same-process, fire-and-forget, for decoupling business logic) - see the comment at the `eventEmitter.emit` call site in `rides.service.ts`. | **Yes - blocking.** The Dispatch module task must add an `@OnEvent('ride.requested')` listener (or equivalent) before Phase 4's "nearest driver is offered the ride" deliverable can actually work end-to-end. **CLOSED by the Dispatch module task**: `dispatch/dispatch.service.ts` now has `@OnEvent('ride.requested')` (`DispatchService#onRideRequested`), which starts the nearest-driver offer cascade for every newly-`SEARCHING_DRIVER` ride. | 11 | Dispatch / Matching | `DriverMatcherService`'s `LOCATION_STALENESS_WINDOW_MS` (how old a driver's pushed `current_latitude`/`current_longitude` may be before it's no longer trusted for matching) has no doc-specified value anywhere in `architecture.md`/`specification.md`/the booking spec - it's a pure product-tuning knob. | Chose **5 minutes** as a sane default: long enough to tolerate `specification.md §6`'s driver-app push cadence (~3-15s moving/stationary) plus normal backgrounding/network jitter without constantly dropping otherwise-fine drivers out of matching, short enough that a driver who went offline without updating availability (app killed, phone died) doesn't keep getting offered rides for hours. | 12 | Dispatch / Tests | `assignment.service.integration-spec.ts`'s concurrency races (`accept()` same-ride and same-driver-two-rides) run against the one shared local Postgres instance every other integration test also uses, and `DriverMatcherService#findCandidates` is intentionally unscoped (it reads every matching driver row in the table, not just a given test's own fixtures) - so a different suite's leftover/concurrent driver rows could, in principle, change which candidate is "nearest" for an unrelated test. | Worked around by giving `assignment.service.integration-spec.ts` its own pickup point (`1.0, 1.0`), deliberately far from `driver-matcher.service.integration-spec.ts`'s (`24.9, 72.7`), so any other suite's seeded drivers land too far away to ever outrank this suite's own "nearest"/"next nearest" fixtures. Also worth recording: the same-driver-across-two-rides race test is a **real concurrent** `Promise.allSettled` (not a sequential substitute, which the task brief allowed as a fallback) - it passed repeatedly across multiple manual runs, relying on Postgres's default READ COMMITTED behavior (a blocked `UPDATE` re-evaluates its `WHERE` clause against the just-committed row once unblocked) to serialize the two transactions' competing claim of the same driver row correctly. | **Yes** - if dispatch integration tests ever run against a non-default isolation level, a transaction-pooling connection pooler, or much heavier CI parallelism, revisit whether a more systematic per-test "pickup island" (or serializing these specific tests) is needed; today's two-far-apart-coordinates workaround is informal. |

| 14 | Dispatch / Review fix | Reviewing the Dispatch module task's `assignment.service.ts` before commit: `accept()` and `reject()` both call `findPendingOffer` *before* opening their `db.transaction`, then inside the transaction updated the `ride_offers` row keyed only on `id` - not conditioned on `result = 'PENDING'`, unlike the (correct) pattern the same task used for the driver/vehicle claims and in `ride-offer-timeout.processor.ts`. That left a real TOCTOU gap: if the 15s timeout fired in the gap between the pre-transaction lookup and the update, `accept()` would silently overwrite an `EXPIRED` offer back to `ACCEPTED` (letting an already-timed-out driver still win the ride), and `reject()` would overwrite it back to `REJECTED` and call `advanceToNextDriver` a second time (double-offering the next candidate alongside the timeout processor's own call). | Fixed in review, before commit: both updates now condition on `and(eq(rideOffers.id, ...), eq(rideOffers.result, 'PENDING'))` and check the returned row - `accept()` throws `ConflictException({code: 'OFFER_NO_LONGER_PENDING'})` (rolling back the whole transaction, including the ride/driver/vehicle claims already applied in the same transaction); `reject()` simply skips its own `advanceToNextDriver` call when it loses the race, since the timeout processor already made that call. Full test suite re-run after the fix - all 46 tests still pass, no regressions. | No - fixed; flagging for visibility only. A dedicated test for this exact race (offer expires mid-accept) would be a nice-to-have but isn't blocking. |
